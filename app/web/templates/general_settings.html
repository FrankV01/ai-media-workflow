FourthWall

Publishes the job's delivery archive as a digital product. The ZIP itself is hosted on Cloudflare R2 (configured below) — the product's downloadable file is a small download document carrying the R2 link, and the smallest per-variant renderings become preview images. The listing runs when fourthwall_listing is a step in the workflow (edit steps on the workflow page). API credentials are read from FOURTHWALL_API_USER / FOURTHWALL_API_PASSWORD in .env — they are never stored in the database.

Products are created hidden unless "Publish on create" is on — the API cannot publish later, so hidden products are published manually from the Fourthwall admin.

$description/$tags come from the Social Media Specialist's marketplace post (falling back to the Art Director's brief); $title is the shoot name; $attribution is the artist attribution above.

Always shown after the description on the product page — clears expectations that the images are AI-generated. Save with this field empty to disable it.

The product category can't be set through the API — assign one per product in the Fourthwall admin; Fourthwall maps it to the sales-tax code.

Cloudflare R2

Hosts the delivery ZIP buyers download — the archive is too large for FourthWall's digital-file limit, so cloudflare_r2_uploader puts it in this bucket and the product links to its public URL. The S3 API credentials are read from CLOUDFLARE_R2_ACCESS_KEY_ID / CLOUDFLARE_R2_SECRET_ACCESS_KEY in .env — they are never stored in the database.

Enable the bucket's r2.dev public access or attach a custom domain in the Cloudflare dashboard, then paste its URL above — the S3 endpoint alone cannot serve buyer links. Public links are unguessable by key but reshareable.

PayHip

PayHip cannot be automated: its public API offers no endpoint for creating products or listing files for sale — only sales notifications (IPN/webhooks) are exposed. To sell a delivery archive on PayHip, create the listing manually in the PayHip dashboard and upload the ZIP by hand.

What goes into a delivery

Delivery archives intentionally contain the complete job output — renderings, cutouts, and reports — plus the full creative process record (_delivery/creative_process.md), which includes internal prompts, model settings, and request parameters. Application credentials and environment configuration are not exported; prompts, outputs, and anything you write into them ship verbatim.
